Theory

Understand the important concepts before running the simulation.

02 / THEORY

1. What is a DAG?

A Directed Acyclic Graph is a set of tasks connected by one-way dependency arrows. It has no circular dependency. If task B depends on task A, A must complete successfully before B can start.

Extract→Validate→Enrich↘Aggregate←Score

In the ORBIT example, Enrich and Score both depend on Validate. They are independent of each other and can be scheduled concurrently. Aggregate waits for both.

2. Dependency-aware scheduling

A task is eligible to run when every dependency is in the SUCCEEDED state and worker capacity is available. Tasks waiting for prerequisites remain pending; eligible tasks can become ready and then running.

Ready(task) = all dependencies succeeded

3. Retries and backoff

A temporary error does not always mean the workflow must fail. ORBIT can schedule another attempt after a short delay. This demo uses exponential retry backoff.

delay = min(0.3 × 2^(attempt − 1), 2.4) seconds

These delays are shortened for teaching; real systems use workload-appropriate policies.

4. Output checkpoints

After a successful task, ORBIT saves its output checkpoint in SQLite. This makes the result inspectable and gives the demo a record of completed work rather than relying only on the screen.

5. Dead-lettering and recovery

If a task keeps failing until its retry limit is exhausted, it is marked DEAD_LETTERED. Downstream tasks are blocked because their required input is unavailable. The operator can manually recover that task and its downstream dependants.

6. Idempotency and replay audit

An idempotency key helps the system recognise repeated completion for the same task so the demo does not create a second checkpoint. The replay audit reads stored state and checkpoints after emitting a restart-style marker.

Scope limitation: Worker crash, duplicate delivery, and restart/replay are injected teaching rehearsals. They do not kill a real operating-system worker, publish a second broker message, or restart the running web process. Queue selection and workers run inside one Python service.

Procedure

Follow these steps in order and note what changes in the graph.

03 / PROCEDURE
Read the Aim and Theory.

Understand DAG dependencies, task states, retry behaviour, and checkpoints before starting.

Open Simulation and choose Happy Path.

Click Run Simulation. Wait for the workflow to finish and watch the dependency graph and event timeline.

Inspect the independent branches.

Select Enrich or Score in the graph. Notice that both wait for Validate, but neither depends on the other.

Run Transient Failure.

The Enrich task fails on its first attempt, enters retry, and should later succeed. Compare attempts and events with Happy Path.

Run Poison Task.

Score repeatedly fails and is dead-lettered. Observe which downstream tasks become blocked, then use Recover task & downstream to rerun that work.

Try one additional rehearsal.

Choose Worker Crash, Duplicate Delivery, or Replay Audit. Read the timeline messages and keep the distinction between an injected simulation and a real distributed failure clear.

Record observations and take the self-test.

The Observations section uses the most recent API-reported run values. The self-test checks your understanding and displays feedback.

Tip: Wait until a run reaches SUCCEEDED or FAILED before starting the next experiment. The simulator updates the current graph approximately twice per second.
